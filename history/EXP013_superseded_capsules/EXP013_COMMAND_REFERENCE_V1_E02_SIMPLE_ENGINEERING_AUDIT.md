# EXP013 E02 SIMPLE — engineering audit

## Scope and decision

This is a separate engineering amendment to EXP013_COMMAND_REFERENCE_V1, replacing E01/P01's orchestration, not its scientific study. The user reports **zero completed scientific fits**. The successful earlier EXP006/EXP007 sources were inspected: explicit job loops, deterministic package identities, local fit archives, SHA-verified persistent copies and verified completed-job reuse are the useful precedents. Their old model settings and forecasting selection criteria are not imported into EXP013.

The reported 80GB and 40GB capacities are different and explain at least one exact-environment rejection. E02 creates a new honest runtime identity rather than relabelling an 80GB gate. Existing E01/P01 state is neither edited nor imported as 40GB authorisation. Original data, EXP012 outputs, official archives, protocol, architecture, scorer, evaluator and the 22-job/hyperparameter factory remain byte-identical to E01. E01's already disclosed mission-scaler correction is retained.

## Minimal execution path

The notebook mounts Drive once; runs the original training loop in one unbuffered child per action; uses a small stdout/deadline launcher; and calls the original pipeline for selection, freeze, confirmation, scoring and evaluation. E01's runtime wrapper, Drive API authentication framework, performance profiler, environment migration overlay and comprehensive repeated runtime test framework are not used. They remain preserved as historical source/evidence. The E01 streaming checkpoint codec, exact batch sampler/collator and proven score cache are reused.

`src/train.py` has additive observation contexts and an optional finite-gradient check. No loss, model expression, draw order, optimizer setting, batch size, sampling rule, scheduler behaviour, stopping rule or checkpoint objective changes. `src/execution_runtime.py` adds optional observation hooks; inactive hooks are no-ops. Changes are identified member by member in SOURCE_MANIFEST.json; the original package manifest is retained in the parent release and replaced only in this new package to bind its actual bytes.

## Gates and scientific boundaries

The first actual hardware gate is one **real MSL graph FIT+STOP epoch**, not a reduced surrogate. The full epoch and one second-epoch update are retained for the scientific fit. Two restores from the same epoch boundary replay the next update and compare model/Adam/RNG/sampler/objective state exactly. Replaying an unfinished smoke restores its preserved boundary and never repeats a completed full epoch.

This intentionally changes the original engineering gate order: one developmental epoch is allowed to establish the first hardware gate before validating unrelated baselines. It does not authorise the remaining study, selection, confirmation or TEST access. This sequencing is explicitly authorised by the user's request for a real first-epoch smoke. All ten full-shape role checks still have to pass before the original `fit_and_select` path is invoked. The first MSL graph role is supplied by the smoke; the other nine use full frozen shapes and exact serialized/restored update checks. A final gate verifies the complete ten-role roster, native batch sizes, identities and evidence hashes. Partial gates and changed batch sizes cannot authorise training.

Official GDN forward and parameter/input/embedding gradients retain the original independent dense equation comparison. CATCH checks its official loss, carried mask gradients, original pre-backward mask-optimizer ordering, unstepped scheduler states and native score. Constant/sparse native-score failures are recorded using the original policy; no epsilon or replacement score is added. Additional batch checks are private engineering models, discarded after testing, not extra scientific fits or selected checkpoints.

TRAIN-only fitting, STOP selection, 80–90% calibration/selection, frozen study before 90–100% synthetic confirmation, subsequent TEST scoring, complete score-seal verification before annotation parsing, historical LSTM reuse and the common evaluator all remain unchanged. No NASA annotations or TEST float arrays were opened during this amendment. Inherited historical label-derived reports remain opaque input evidence as previously documented; this is not physical isolation from all historical information. NASA conclusions remain retrospective.

## Resource audit and runtime uncertainty

The frozen workload is in RESOURCE_REQUIREMENTS.json. New-model FIT workloads are MSL 32,321 windows / 127 batches and SMAP 79,331 / 310. GDN uses MSL 1,089 FIT + 365 STOP batches for at most 30 epochs, SMAP 2,579 + 863. CATCH uses MSL 233 FIT + 92 STOP batches for at most five epochs, SMAP 567 + 216 for at most ten.

CATCH MSL has **210,881,152 parameters** (a **3.142 GiB** dense estimate at 16 bytes/parameter for FP32 parameters, gradients and two Adam moments, excluding activations, FFT, attention, workspaces, serialization and transient allocation). CATCH SMAP has **53,464,208** (about **0.797 GiB** on the same accounting). Unused registered parameters do not allocate gradients or Adam moments, so this dense estimate is not an exact state-memory measurement or a formal peak-memory lower bound. GDN's models are small but its batch count is much larger than the new graph fits. The CATCH MSL dense frequency heads dominate its parameter count. None of these figures establishes 40GB peak feasibility or a runtime speedup.

Every actual Colab probe includes full-batch forward/backward, both relevant optimizers, serialization/restoration and exact update replay; peak allocated/reserved memory is measured. Native inference is also checked for CATCH. An OOM, nonfinite check, failed replay, operation deadline, or insufficient observed memory margin stops without reducing settings or marking a baseline complete. A need for 80GB would be a feasibility finding, not permission to weaken the experiment. Environment changes after progress remain explicit integrity stops.

First-operation timing distinguishes initialization, host preparation/transfer, clean/injected forward, injection, scalar synchronization, backward, optimizer, validation and checkpoint I/O. GPU timing is explicitly synchronized in the diagnostic smoke samples and hardware checks; ordinary asynchronous host timing is not called completed GPU timing. Full-epoch elapsed time is measured on the actual workload. Projections extrapolate measured FIT and validation batches to epoch caps and are rough: unknown early stopping, seed effects, contention, synthetic selection, confirmation, TEST scoring and backup costs are not guaranteed. No GPU speedup is claimed. The original SIGKILL remains of unconfirmed cause.

## Persistence and recovery

All scientific I/O remains on local `/content`. Backups are compulsory synchronous operations at safe batch/stage boundaries. Checkpoint binaries are immutable content-addressed Drive objects; small files are a locally created ZIP. Every new object is staged with a unique partial name, read back and SHA-verified before promotion. A versioned manifest plus hashed completion receipt is published only after every object is verified. Objects unchanged in size/mtime/inode are reused within the verified session; restoration always rehashes their bytes. Two complete generations and all objects needed by either are retained. There is no automatic deletion of E01/P01 state.

Restore verifies completion, receipt hash, source identity, object hashes, path safety, exact file roster and actual frozen runtime before promoting recovered work. Corrupt latest generations can fall back to an earlier verified generation; an environment mismatch never silently falls back to a different environment. Incomplete objects cannot become a recovery point. Failed uploads stop training; the prior good backup remains usable. Completed fit identities, selected hashes and frozen study membership are checked by the original pipeline. One notebook/VM per backup directory is required; mounted Drive is not a distributed transactional database.

The practical training-compute loss target is 600 seconds plus the current batch; backup copying time and long atomic scoring calls prevent a strict 15-minute wall-clock guarantee. A local Unix lock prevents duplicate workers in one VM, and the retained parent-death guard prevents a live orphan after kernel death. The launcher enforces operation, epoch and probe deadlines from a small nested status journal, without profiling. A browser disconnect does not itself guarantee either survival or failure.

## Validation and remaining limitations

BUILD_VALIDATION.json and the delivered test logs identify actual tests, their results and source hashes. Existing scientific and execution suites are retained. New tests cover simple Drive-style copies, interrupted upload, receipt/object corruption, two-generation fallback, source identity, explicit 80GB/40GB mismatch, complete VM-reset exact training restoration, completed-job reuse, smoke replay and replay interruption, all-family optimizer/mask resume, full-gate/batch rejection, stage ordering, label gate, bounded worker shutdown and SIGKILL reporting. The fictional end-to-end fixture exercises 22 fits and all final boundaries with the E02 backup and score-cache hooks. Tiny fictional test configurations never replace scientific factory settings.

**Not executed here:** actual A100 40GB/80GB model throughput, full native GPU capacity, actual GPU byte-identical replay, or authenticated live Google Drive/FUSE transfers. The notebook measures these before remaining scientific fitting. CPU/mocked tests are implementation evidence only. There is no claim of successful EXP013 anomaly-detection results, 40GB feasibility for every model, or independent real-anomaly confirmation.
